# Rule sign-off

This sheet lists every rule in `rules/clinical_rules.yaml` (version 0.2) for the clinical advisor. It is part of the ReproSense safety case (issue #45). It does not change any rule.

**Who signs.** The clinical advisor signs, and must be a clinician. For each row they fill in Reviewer, Date, Decision and Comment. The YAML header asks for the same thing ("reviewer: ________ (clinician name/date)", line 4). That line is still blank. No clinician has been recruited yet (Q18). A team approval, such as Krishna's review of PR #40, is not a clinical sign-off. Neither is a review by a role agent in `.claude/agents/`. When every row is decided, the advisor also signs the reviewer line in the YAML.

**What the decision means.**
- **Agree:** keep the rule as it is: what it checks, its threshold, its wording and its source.
- **Change:** keep the rule, but change something. Write what in Comment: a threshold, the wording, the source, or who the rule applies to. The team makes each change in its own pull request. That pull request names this row, adds a test, and is recorded in `docs/safety/CHANGE_LOG.md`.
- **Remove:** the rule must not run in a pilot. The engine has no switch for a single rule: it runs every rule in the YAML. So removing a rule means deleting it from `rules/clinical_rules.yaml` in a reviewed pull request.

**Synthetic data only.** The demo uses synthetic data only (CLAUDE.md rule 4). Everything in `data/` is fictional, and every test named below runs on synthetic records. The YAML header says a clinician must review the file before any real-world use. This sheet is for that review, before a pilot.

**What the app cannot record yet.** Some rule parts depend on facts the app never sets. Sign-up (`SignupIn` in `backend/app/api/demo.py`) offers five life stages: periods, trying to conceive, pregnancy, after birth and perimenopause. It does not ask about breastfeeding, hormonal contraception or age at first period. No route changes these later. So:
- Life stage "postmenopause" is never set. No persona has it. Only one test sets it (`test_rules.py::test_rf2_late_period_does_not_count_after_menopause`). The "after menopause" parts of RF3 and RF2 never apply in the app.
- Breastfeeding and hormonal contraception are set only for the seeded personas. For a woman who joins, both are always "no".
- The rows below and "Gaps found in review" say where this matters.

## How to read the table

- Rules are in YAML order. Red flags come first, because they run first. Then come observations and care gaps.
- **Threshold** is the rule's `when` line, copied from the YAML. Numbers that live in code, not in the YAML, are added under it.
- **Day window:** these red flags check each day she logged, from 14 days ago up to today. The 14 days is a default in `backend/app/config.py` (`red_flag_window_days`). It still needs clinician sign-off (Q17).
- **Source** ids are listed in `knowledge_base/sources.yaml`.
- **Pinned by test** names the tests in `backend/tests/` that assert the rule. Three checks in `test_rules.py` cover every rule, so they are not repeated in each row: `test_every_rule_parses_and_only_uses_known_names`, `test_rule_copy_has_no_banned_phrases` and `test_rule_sources_exist`.
- **Persona checks** means `test_rules.py::test_persona_gets_expected_observations`, `test_engine_matches_generator_self_check`, `test_observations_explain_themselves` and `test_supporting_entries_exist_in_her_record`, plus `test_api.py::test_quality_panel`. They run the rules on the 8 synthetic personas. They check the exact set of cards each persona gets, and that each card points to real entries and sources.
- The card wording (title, message, explanation, next steps) is in the YAML too. A "change" can cover wording.
